## What & Why

After Slice 1, the tech's Submit dialog shows the real bill. But while working, the tech still sees
a wrong number on every finding with quantity above 1.

In service mode, the finding form prefills **Labor hrs** with the catalog default for one unit
(`artifacts/irrigopro/src/pages/wet-checks/ZoneScreen.tsx:117`) and lets the tech step it
(`:394-401`). The zone's finding list then shows that value (`:1830`). The bill ignores it: labor
comes from zone hours, which are catalog × quantity (`storage.ts` `_recomputeZoneRepairLaborIfAuto`).
So 3 heads shows **0.25h** on the finding and bills **0.75h**. The stepper is also misleading — a
tech who raises it believes labor went up, and the bill never sees it.

This ticket makes each service finding's hours equal catalog × quantity, shown read-only, and makes
the server store that value no matter what the client sends.

## Design context (locked decisions — do not relitigate)

1. **Service-mode finding hours are derived, not entered (decided, Randy 2026-09-29).**
   `laborHours = catalog defaultLaborHours × quantity`, same arithmetic the bill uses. The tech
   cannot edit it. Zone-level adjustments stay on the existing zone card (decision 5).
2. **The server is authoritative.** For a service-mode, non-`custom_review`, billable finding
   (create: `repairedInField: true`; patch: `repairedInField: true` in the body or stored
   `resolution = "repaired_in_field"`), the server overwrites `laborHours` with the catalog value and
   ignores the client's number. This also covers the Expo app and any queued offline payload.
3. **No 0.25 snapping for these findings.** The stored value must equal the zone contribution
   exactly, and catalog values need not be quarter-hours (Artisan Pines billed 24.05h). The Task
   #1757 floor and quantization still apply to inspection mode and to non-billable service saves.
4. **Inspection mode is unchanged.** Its "Est. labor hrs" stepper stays editable and feeds the
   estimate (`storage.ts` convert path, `calc(f).laborHours`). Every guard below is service-only.
5. **The zone card "Repair labor for this zone" (`ZoneScreen.tsx:2089-2131`) is not touched.** It is
   the one place a tech can override a zone's hours; the bill and Slice 1's preview already honor it.
6. **No backfill.** Findings already saved on in-progress wet checks keep their stored value until
   next edited. Per-finding hours are display-only for billing; the Submit total (Slice 1) is already
   correct for them. Submitted wet checks are never rewritten.
7. **Catalog lookup key.** Server: `resolveIssueTypeKey` against `listAllIssueTypeConfigs(companyId)`
   (active and inactive — the same set the zone recompute uses, `storage.ts:9815-9817`). Client: the
   `cfg` it already resolves (`ZoneScreen.tsx:98`). If they ever disagree for a legacy key, the
   server's stored value wins on the next refetch.

## Done looks like

- Service wet check, new finding, head replacement: qty 1 shows **Labor hrs 0.25**; changing qty to
  3 immediately shows **0.75** with `0.25 × 3` underneath. There is no stepper.
- Saving and reopening shows 0.75; the zone's finding list row reads `qty 3 · 0.75h`.
- Editing an existing finding's quantity from 3 to 5 stores and shows 1.25.
- A PATCH or POST that sends `laborHours: "4.00"` for a service billable finding stores the catalog
  value, not 4.00.
- Inspection wet check: the stepper is present, editable, and saves as it does today.
