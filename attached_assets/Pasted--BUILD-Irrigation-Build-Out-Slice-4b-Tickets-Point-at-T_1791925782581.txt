# BUILD - Irrigation Build-Out Slice 4b - Tickets Point at Their Controller

**Depends on no other task.** Written against main at `f09887fc` (Slice 4a merged).

## Why

Every ticket stores its location as text: `controller_letter` + `zone_number`. The `controller_id` column on the six document tables was added by migration 0018 and **nothing writes it**. Only `wet_check_zone_records` gets one.

That breaks billing by controller and zone, for two reasons:

1. **Letters can be edited.** The controller PATCH accepts `letter`. If someone relabels Controller C as E, every old ticket that says "C" now points at a different controller, or at none.
2. **The picker ignores the branch.** `work-location-controls.tsx` always loads the customer-level controller list (`/api/properties/:id/controllers`, no `?branch=`). For a multi-branch customer, a tech filling out a ticket for a branch sees the customer-level list. That GET also lazily seeds "Controller A, B, …" into the customer-level bucket from `customers.totalControllers`. The branch's real controllers never show.

This slice fixes both going forward. Historical tickets are filled in by Slice 4c.

## Decision: no `profile_zone_id` column

The audit planned a `profile_zone_id` on every document. **It is dropped.** In `irrigation_profile_zones`, `(company_id, controller_id, zone_number)` is unique (`uniq_irr_pzone_number`), and `_reconcileControllerZones` restores a retired zone by reusing its row. A controller's zone N is therefore the same row forever. Once a ticket has `controller_id`, its `zone_number` identifies the zone exactly. A second id would be a copy that can disagree with the first, which breaks Randy's no-duplicates rule.

## Rules

1. **Edit existing pages only.** No new pages, routes, endpoints or workflows.
2. **Tenant isolation.** Controller lookup is always scoped by the **document's own** `company_id` and `customer_id`, never the request's alone. A letter that matches a controller in another company is never stamped.
3. **Never block a save.** If a letter does not resolve to exactly one controller, save the ticket with `controller_id = null`. Log a warning (`op: "stampControllerId"`) with the company, document table, document id and letter.
4. **`controller_letter` and `zone_number` stay** as written. They are the snapshot shown on PDFs and screens. Nothing reads `controller_id` for display in this slice.
5. **Wet-check scope (Rule 5).** Wet-check capture and zone records are untouched; they already stamp `controller_id`. The only wet-check change is that `convertWetCheckToWetCheckBilling` copies the zone record's `controllerId` onto the estimate items and work-order items it creates. Both modes (service and inspection) go through that one function.
6. **Off limits:** the mobile app, site-map files, PDFs, invoice generation and billing math, and `total_zones`.
7. **Tests join existing lanes** in `scripts/validation-lanes.json`. Do not register a new validation command or workflow. The manifest guard rejects duplicate entry names and commands.

## Changes

### 1. One resolver in storage

Add to `IStorage` and `DatabaseStorage` in `storage.ts`, next to `listCurrentZoneSummaries`:

```ts
resolveControllerIdsByLetter(
  q: DbExecutor,
  scope: { companyId: number; customerId: number; branchName: string | null },
  letters: (string | null | undefined)[],
): Promise<Map<string, number | null>>
```

- Branch key: `(branchName ?? "").trim()`. This matches how `irrigation_controllers.branch_name` stores the customer level as `''`.
- Letters are uppercased and trimmed. Null and empty letters are skipped.
- Use one query, `WHERE company_id = $1 AND customer_id = $2 AND branch_name = $3 AND upper(letter) IN (...)`.
- A letter with exactly one match maps to that controller's id. Zero matches, or two or more (legacy duplicate letters; the unique letter index is still commented out in the schema), map to `null`.
- Empty input returns an empty map without querying.

Add a private helper `_stampControllerIds(q, scope, rows, table)`:

- For each row object that **has the `controllerLetter` key**, set `controllerId` from the map. A null letter sets null.
- Rows without the key are returned untouched, so partial updates that never mention location keep their stored `controllerId`.
- Log the rule 3 warning for each non-null letter that resolved to null.

### 2. Stamp at every storage write that carries a location

Call the helper in each method below, inside the method's existing transaction or executor. The scope comes from the document being written:

- **Item rows:** company, customer and branch come from the parent estimate or work order.
- **Headers:** an update takes values from the patch, falling back to the stored row.

| Method | What gets stamped |
|---|---|
| `_writeEstimateWithItems` | estimate header and each estimate item |
| `updateEstimate` | header, when the patch has `controllerLetter`, `branchName` or `customerId` |
| `updateEstimateWithItems` | header and every re-inserted item |
| `_writeWorkOrderWithItems` | work order header and each item |
| `createWorkOrderFromEstimate` | work order header and items (resolved again, never copied from the estimate's `controllerId`) |
| `approveEstimateAndCreateWorkOrder` | same as above |
| `updateWorkOrder` | header, when the patch has `controllerLetter`, `branchName` or `customerId` |
| `addWorkOrderItem` / `updateWorkOrderItem` | the item (`updateWorkOrderItem` only when the patch has `controllerLetter`) |
| `replaceWorkOrderItemsInTransaction` / `replaceWorkOrderItemsWithResync` | every inserted item |
| `attachWorkOrderZonePhoto` | the photo (scope from its work order) |
| `createBillingSheet` / `updateBillingSheet` | header (an update only on the same three keys) |
| `convertWetCheckToWetCheckBilling` | estimate items and work-order items: copy `controllerId` from the source zone record when the row came from one, otherwise resolve |

**When a header's `branchName` or `customerId` changes** in `updateEstimate`, `updateWorkOrder` or `updateBillingSheet`, restamp that document's items as well, in the same transaction. Their letters now belong to a different controller list. Billing sheet items carry no location and are not touched.

Before finishing, grep `storage.ts` and `routes/**` for every `.insert(` / `.update(` on `estimates`, `estimateItems`, `workOrders`, `workOrderItems`, `workOrderZonePhotos` and `billingSheets` whose payload can include `controllerLetter`. List any write not in the table above in the completion report, with what you did about it. Do not stamp inside `lib/migrations/**` or `scripts/**`.

### 3. The picker loads the ticket's branch

`work-location-controls.tsx`:

- **New prop:** add `branchName?: string | null` to `WorkLocationControlsProps`.
- **Query:**
  - key: `["/api/properties", customerId, "controllers", branchName || null]`;
  - explicit `queryFn`: `cachedApiRequest` of `/api/properties/${customerId}/controllers`, plus `?branch=${encodeURIComponent(branchName)}` when `branchName` is non-empty.

  This is the same key shape `ControllerSelectionPage` already uses, so the two share cache entries. Existing invalidations of `["/api/properties", customerId, "controllers"]` still match by prefix; check this in a test.
- **Clearing on branch change:** extend the existing customer-change clear to branch changes, using a second `previousBranchRef` with the same rules. Clear `controllerLetter` and `zoneNumber` only when the branch actually changes after mount, never on mount and never because a fetch came back empty. Keep the comment block above the effect and add one line explaining the branch case.

Pass the prop from every caller:

- **`customer-location-step.tsx`:** add `branchName?: string | null` to its `Props` and forward it.
- **`work-order-wizard.tsx`, `estimate-wizard.tsx`, `billing-sheet-wizard.tsx`:** pass `branchName={customerStep.branchName}` to `<CustomerLocationStep>`. The branch is chosen in the customer step, which comes before the location step in all three.
- **`work-order-completion.tsx`:** pass `branchName={selectedBranch || workOrder.branchName || null}`. When the tech picks a branch at completion, the submit's `updateWorkOrder` carries `branchName`, and change 2 restamps the header and items.

### 4. Deleting a controller with history

Once tickets point at controllers, a controller with history can no longer be hard-deleted: the foreign keys on documents and wet-check zone records block it. Today that already happens for controllers with wet-check history, and the user sees "Could not delete controller — please retry", which is wrong; retrying never works.

In the DELETE handler in `irrigation-profile-routes.ts`, catch Postgres error code `23503` and return:

- status **409**;
- body `{ message: "This controller has work history (tickets, estimates or wet checks) and can't be deleted. Turn it off instead." }`.

The grid's existing `onError` toast already shows `err.message`, so no web change is needed. Every other error keeps the current 500.
