## 2. Restore the evidence behind Step 1

#2046 says "prefer the billed-price header with nullish precedence." That is the right instruction but it reads as a style preference. It is not. Three readers exist and no two agree:

| Location | Expression | On a stored `"0.00"` |
|---|---|---|
| `storage.ts:6536`, `:7002` | `wo.partsSubtotal ?? wo.totalPartsCost ?? 0` | returns 0 |
| `routes.ts:6934` | `wo.partsSubtotal \|\| wo.totalPartsCost \|\| '0'` | `"0.00"` is **truthy** — returns it, never falls through |
| `routes.ts:7182` | `parseFloat(wo.totalPartsCost \|\| '0')` | legacy column alone |

The `||` → `??` change at 6934 is the entire reason that line is in scope. Without this table it looks cosmetic and is likely to be skipped.

**Additional constraint, omitted from #2046:** where the resolver cannot be imported without coupling route code to the PDF subsystem, mirror it with a comment naming `pdf-view-model.ts` as the source of the rule. **Do not invent a third precedence.** There are already three; the ticket exists partly because of that.

## 3. Restore the exact write, including tenancy in the `where`

#2046 Step 4 says "within tenant scope." That is ambiguous in a way that matters, because the file the executor is told to model on does it the weaker way: `repair-ticket-total-drift.ts:114-118` carries `companyId` on the candidate row but **omits it from the update's `where` clause**, scoping only at query time. Modelling on that file without this note reproduces the gap.

The write is:

```ts
await tx.update(workOrders).set({
  partsSubtotal: itemsTotal.toFixed(2),
  totalPartsCost: itemsTotal.toFixed(2),
}).where(and(eq(workOrders.id, id), eq(workOrders.companyId, companyId)));
```

`companyId` appears in the `where` on every select **and** every update. Never write `labor_subtotal`, `total_amount`, or any invoice column. The tenancy test asserts the update clause specifically, not just the select.

## 4. Restore the two operational gates

**Stop-if-zero (missing from #2046 Step 7).** Before writing anything, ship #2045 and read its `pdf_parts_subtotal_healed` counter across a regeneration of recent invoices. If it reports zero heals, **stop and report** — the migration is a no-op and Steps 1-2 are the whole ticket. #2046 has "stop if the population is unexpectedly broad" but not this case, and the zero case is the more likely of the two.

**Why the confirmed rows are safe (missing from #2046's What & Why).** The arithmetic is the justification for the invariant and should be in the ticket, because anyone tempted to relax the equality check needs to see it:

- WO-1783955816671-314 today: parts `0`, labor `5,270.00`, stored total `8,401.70`. Canonical (`parts + labor`) = `5,270.00`, which is **below** stored, so `repair-ticket-total-drift-v1`'s add-parts-only rule (`:223-224`) skips it.
- After repair: parts `3,131.70`, canonical `8,401.70`, stored `8,401.70` — **exactly zero drift**, permanently outside the candidate set.

That equality is why the repair is safe on these rows and why rows failing it must be skipped: on those, correcting parts upward can push canonical above stored, and `recomputeInvoice` (`:146-157`) then rewrites the parent **invoice's** `parts_subtotal`, `labor_subtotal` and `total_amount` — on an invoice already sent to the HOA and in some cases already pushed to QuickBooks.
