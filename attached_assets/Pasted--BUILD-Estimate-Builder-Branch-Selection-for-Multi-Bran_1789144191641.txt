# BUILD — Estimate Builder: Branch Selection for Multi-Branch Customers

**What & Why**

Pick a multi-branch customer in the **Billing Sheet Creator** and a required "Branch Location" card appears before you can continue. Pick the *same* customer in the **Estimate Builder** and nothing appears — the wizard goes straight from Customer to Scope of Work and the estimate saves against the parent with no branch. The estimate builder is the **only** ticket-creation flow in the app that does not capture a branch; billing sheets, work orders and wet checks all gate on it.

**The column already exists and the downstream already reads it.** `estimates.branch_name` shipped under Task #315. The PDF renders a `Branch:` line from it, the estimate → work-order conversion carries it, and the API already accepts it (`insertEstimateSchema` is generated from the table; `processEstimatePayload` spreads it through). **No schema change, no migration, no `pnpm db push`.** Nothing ever *writes* the value — that is the whole bug.

**Consequence.** A repair estimate for a customer's north branch approves into a work order with no branch and bills to the parent. The tech is then asked to pick a branch at *completion* time as a rescue (`work-order-completion.tsx:308`) — the exact "ask the tech to remember it later" failure Rule 4 exists to prevent. The branch is known at estimate time and must be captured there.

**Copy the existing pattern; do not invent one.** `billing-sheet-wizard.tsx` is the reference implementation for every UI decision in this ticket. Same card, same copy, same gate.

**Rules in scope:** Rule 4 (capture at the source, guard at capture time), Rule 8 (one implementation, no options left open), Rule 1 (tenancy — the branch list is read off the already company-scoped customer record; no new query), Rule 7 (screenshot proof for a real multi-branch customer).

### 3. Server gate — one helper, two call sites

**New export in `artifacts/api-server/src/estimate-payload.ts`** (the module both write paths already share for labor-rate resolution — do not create a new file, and do not inline the check twice):

```
// Branch enforcement: if the customer has branches configured, branchName is
// required. Mirrors POST /api/billing-sheets (routes.ts:11535-11544) and
// POST /api/work-orders (routes.ts:13237-13246).
export function resolveBranchGateError(
  customerBranches: unknown,
  branchName: string | null | undefined,
): string | null {
  if (!Array.isArray(customerBranches) || customerBranches.length === 0) return null;
  if (!branchName || String(branchName).trim() === "") {
    return "Branch is required for this customer. Please select a branch before submitting.";
  }
  return null;
}
```
The message is copied verbatim from `routes.ts:11540` so all three flows read identically to the user.

**`POST /api/estimates` (`routes/estimate-routes.ts:457`).** Inside the existing `if (customerId != null)` block (`:512–526`) — the customer is already loaded there as `customer`, so no second query — after the `!customer` 400 and before the labor-rate stamp:
```
const branchError = resolveBranchGateError(
  customer.branches,
  (parsed.estimate as { branchName?: string | null }).branchName,
);
if (branchError) { res.status(400).json({ message: branchError }); return; }
```

**`handleEstimateUpdate` (`:550`).** After `existing` is loaded and `newCustomerId` / `customerChanged` are resolved (`:598–599`), gate on the **effective** customer and the **effective** branch, reusing the `customer` already fetched in the `customerChanged` branch (`:602`) rather than fetching twice:
```
const gateCustomerId = newCustomerId ?? existing.customerId;
const gateCustomer = customerChanged ? customer : await storage.getCustomer(gateCustomerId);
const incomingBranch = (parsed.estimate as { branchName?: string | null }).branchName;
const effectiveBranch = incomingBranch !== undefined ? incomingBranch : existing.branchName;
const branchError = resolveBranchGateError(gateCustomer?.branches, effectiveBranch);
if (branchError) { res.status(400).json({ message: branchError }); return null; }
```

**The gate is unconditional, drafts included (decided).** "Save as draft" is only reachable from step 4 of the wizard (`estimate-wizard.tsx:947–958`), which sits behind the step-1 branch gate, so no legitimate draft save can be blocked. Exempting drafts would leave a writable path that still produces branch-less estimates.

**Legacy rows behave as intended (decided).** An existing branch-less estimate for a multi-branch customer 400s on its next save until a branch is chosen. The wizard shows the required card the moment it opens, so the fix is one click. **Do not add a grandfather clause.**

## Done looks like

- Selecting a multi-branch customer in the estimate builder shows a required Branch Location card, and **Continue** is disabled until a branch is chosen — identical to the billing sheet creator for the same customer.
- A single-location customer shows no branch card and behaves exactly as before.
- Changing the customer clears any previously chosen branch.
- The saved estimate row has `branch_name` set; a single-location estimate has `NULL`.
- Editing an estimate that already has a branch pre-selects it.
- The wizard header reads `Customer · Branch`.
- `POST /api/estimates`, `PUT /api/estimates/:id` and `POST /api/estimates/:id/submit-for-review` all 400 for a multi-branch customer with no branch, and succeed with one. A single-location customer is unaffected on all three.
- Converting a branch wet check to an estimate produces an estimate carrying that branch; approving it produces a work order carrying the same branch.
- The review step, detail modal, public approval page and approval email each show `Branch: <name>` when set and nothing extra when not. The PDF is unchanged.
- **No second copy of the branch-gate logic** — both estimate write paths call `resolveBranchGateError`.

## Explicitly out of scope

- Branch selection in the billing sheet creator, work-order wizard and wet-check flow — all working; referenced only as the pattern to copy.
- Creating or editing a customer's branch list (existing, on the customer profile).
- Back-filling `branch_name` on estimates already created without one. Those stay visibly empty until someone edits them, at which point the gate forces a choice. A bulk backfill would have to guess at billing attribution, and guessing there is worse than an empty field (decided).
- Branch-scoped controller/zone loading in the estimate wizard's Location step. That picker is customer-scoped today; changing it is a separate ticket with its own data questions and is not what is broken here.
