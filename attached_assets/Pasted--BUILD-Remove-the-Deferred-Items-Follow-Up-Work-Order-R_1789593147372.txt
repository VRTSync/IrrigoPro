# BUILD — Remove the Deferred-Items Follow-Up Work Order (Retire #1935)

**Sequenced ticket. Slice 1 must be run in production and verified before Slices 2 and 3 merge.** Slice 3 drops a column that Slice 1 needs the records to still be identifiable by. Slice 1 identifies its targets by `work_order_number` literal, not by the column, so a mis-order is recoverable — but do not rely on that. Run Slice 1 first.

## What & Why

Task #1935 diffs an approved estimate's line items against the items on the completed work order and auto-creates a "follow-up" work order carrying whatever did not match. The match key is `part_name + controller_letter + zone_number + issue_type`.

**That diff cannot distinguish work that was not done from a part that was substituted**, and substitution is the normal case. An estimate is an estimate; the parts and hours differ on almost every job. The work order is created prefilled with the estimate's parts (`storage.ts:4018` `createWorkOrderFromEstimate` copies `estimate_items` onto the work order), the tech edits that list down to what he actually installed, and completion uses replace-not-append semantics. Every quoted part the tech did not use therefore reads as deferred work.

Measured in production at Woodglenn Squares HOA on 2026-08-21. Three completed, manager-approved, billed work orders each grew a phantom follow-up at the moment of the completion submit (follow-up work order numbers embed `Date.now()`: `1787333695634` = 11:34:55, `1787333883734` = 11:38:03, `1787334011979` = 11:40:11, matching the parents' completion times to the second):

| Parent (billed, Invoice #171) | Phantom follow-up carries | What the parent actually carries |
|---|---|---|
| WO-1785869292161-458 valve replacement | 1" Rain Bird Scrubber Valve (PESB), $350 | diaphragm kit + latching solenoid — rebuilt, not replaced |
| WO-1785869264925-44 leak 11879 Harrison | 1" PVC slip-fix, coupler, glue, Class 200 pipe | .75" poly pinch clamp + insert coupler |
| WO-1785869241143-67 lateral line break | 1" PVC coupler, slip-fix, glue | nine poly insert fittings |

PVC quoted, poly in the ground, every time. The repair was complete in all three cases. The result is a non-continuous billing line: one repair split across two work orders, with the parent billed and locked so the phantom can never be reconciled back into it.

**The decision (decided).** Nothing downstream second-guesses a technician's completion by comparing parts lists. Parts determine what is billed; they say nothing about whether the work happened. Marking the ticket complete means the referenced fix is done — the same trust model already applied to billing sheets. The diff and everything built on it is removed, for every work order, in every mode.

**Explicitly out of scope.** The punch-list problem this mechanism was invented for — a 162-line inspection estimate where 18 repairs went untouched and nothing flagged it — is a separate ticket. It is not solved here and must not be patched here with a replacement audit. If a future design starts needing a mechanism to verify a work order was "fully" completed, that is the tell that an inspection punch list is riding work-order rails again; fix the shape, do not rebuild this.

## Additive check — what already does part of this

Nothing else in the repo creates a work order from a diff. `createWorkOrderFromEstimate` (`storage.ts:4018`) is the only other work-order-creating path and is untouched by this ticket. `work_orders_estimate_unique_idx` (#1740) and its 23505 idempotency catch stay exactly as they are. There is no second implementation to consolidate — this is a pure removal.
